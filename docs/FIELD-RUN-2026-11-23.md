# Field run, 2026-11-23: the Fleet Runtime landing campaign's closure records

Use, not measurement. The shipped extraction mode, exactly
as it stands, run over records outside every measured
corpus: the seven per-repo closure audits banked in
fleet-records (chat3-perrepo-closures, arvin through
wayside, the audits of the campaign that landed 171 audit
PRs), each in a bundle carrying a fresh clone of its own
repo, plus the seat's running record (status/chat-3-STATUS.md,
149,758 bytes) in a bundle with no repo, since it spans
seven. No standings change on anything here, and no
pattern proposal comes out of it.

## Verdicts

All eight runs exit 3. No run found a contradicted claim,
and none found a malformed one. Exit 3 everywhere means
the same thing it means by design: trusted claims the
bundle could not answer, and nothing the bundle answered
against the report.

The seven closure audits: 153 claims extracted. 33
verified, all of them commit citations resolving in the
bundled repo. 120 unverifiable. The status record: 434
claims, all unverifiable, as constructed (no repo, no
logs, no records in its bundle).

## Class by class

Commits and full SHAs (gitsha): the audits cite git
objects of three kinds, and the class checks one of them.
Of the audits' 71 full-SHA citations, the 33 that name
commits on the repos' surviving history verified. The
rest name trees and blobs (the audits verify every pushed
file by its blob SHA, so blob citations are their house
style) or objects of another repo (the records repo's
banking commits and the audit files' own blobs there).
Checked firsthand: the tree and blob SHAs the audits cite
are real objects in their repos; they are simply not
commits, and the class resolves commits. Every non-commit
citation therefore lands unverifiable, honestly, and the
distinction is invisible in the verdict unless the detail
line is read with the report open.

Tallies: 74 in the audits, 200 in the status record, all
unverifiable. The bundles carried no logs, and the audits
state gate outcomes in prose. This is the bundle-answers
rule working as designed; it also means a closure audit's
most load-bearing claims, its gate tallies, are exactly
the ones a bundle assembled after the fact cannot answer.
A bundle assembled at closure time, carrying the gate
logs, would answer them.

Pull requests: nearly invisible, and worth stating
plainly. The audits name their pull requests in words
("pull request 115"), a form the measured pattern set
does not take, so across seven audits whose entire
subject is landed pull requests, extraction found one PR
claim (deadbolt's, unverifiable for want of a bundled
record). The campaign's central objects pass through the
tool almost unseen. Recorded here as a field observation;
the fence on this run forbids turning it into a pattern
proposal, and none is made.

Counts: a handful across the runs, all provisional, all
unverifiable (rounds, commits, and files the bundle
cannot recount under the line-count rule). Hash256: three
in the status record, unverifiable, no bundled file
hashing to them.

## What the run establishes

The campaign's closure records contain no claim the tool
could answer against them: zero contradictions across 587
extracted claims. What a post-hoc bundle can verify in
this fleet's closure prose is the commit spine, heads and
merge commits on surviving history, and that verified
clean everywhere it could be checked. The rest of what
these reports assert travels on evidence a bundle has to
be assembled at the time to hold: gate logs for the
tallies, host records for the pull requests, and the
object database itself for the blob citations the fleet's
house style prefers.
